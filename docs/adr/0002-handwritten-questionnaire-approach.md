# ADR-0002: 手書きの問診票の読み取り方式

**Status:** Proposed (PC の仕様と問診票の実物を確認してから決定)
**Date:** 2026-10-22
**Deciders:** 開発者 (息子)、利用者 (父)
**詳しい設計:** [../DESIGN_handwriting.md](../DESIGN_handwriting.md)

## Context
- 読みたいのは印刷物に加えて、**一部手書きの問診票**
- 現行の Tesseract は手書きをほぼ読めない
- オフライン・CPU のみの条件で使える無料の手書き認識は、日本語の手書きでの精度がはっきりしない
- 医療の書類なので、**間違った値が確認されずに残ること**が一番まずい。読めないことよりも危ない
- 問診票はたぶん書式が数種類で固定 (未確認)

## Decision
**問診票を「テンプレート」(白紙の画像＋欄の位置と種類) として登録し、スキャンを白紙に重ねて欄ごとに読む。**
- チェック欄・○囲み → 白紙とのインクの差で判定 (文字認識を使わない)
- 手書き欄 → 差し替え可能な手書き認識エンジン＋信頼度。自信がなければ空欄で「要確認」
- 保存の前に、要確認の欄を画像と並べた確認画面で人が直す
- 第 1 段階では手書き欄は**画像の切り出しだけ**にし、エンジンは評価してから入れる

## Options Considered

### Option A: テンプレート方式＋確認画面 (提案)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Med — 位置合わせ (OpenCV)・確認画面が増える |
| Cost | 無料 |
| Scalability | 問診票の種類ごとに登録が要る。数種類なら問題なし |
| Team familiarity | Med |

**Pros:** チェック欄はほぼ確実 / 欄ごとに答えの種類 (数字・日付) を絞れて手書きの精度が上がる / CSV を 1 枚 1 行 (質問 → 答え) にできる / 手書きエンジンの精度が低くても成り立つ
**Cons:** 問診票の登録作業が要る / 書式が改訂されたら作り直し / 自由な書式の手書き文書には効かない

### Option B: テンプレートなしで、全文を手書き対応 OCR (PaddleOCR など) に通す
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low〜Med |
| Cost | 無料 |
| Scalability | 書式を問わない |
| Team familiarity | Med |

**Pros:** 登録不要 / どんな書類にも使える
**Cons:** チェック・○囲みは読めない / 結果がただの文章で、どの質問の答えか分からない / 誤認識に気づきにくい

### Option C: PC 内で動かす大きな画像言語 AI に問診票ごと読ませる
| Dimension | Assessment |
|-----------|------------|
| Complexity | Med |
| Cost | 無料のモデルもあるが、メモリ 16GB 以上・できれば GPU が要る |
| Scalability | 1 枚数分かかりうる |
| Team familiarity | Low |

**Pros:** 手書き・チェック欄・書式の理解まで最も強い
**Cons:** **読めない字をそれらしく補う** (誤りに見えない誤り) / 配布が数 GB / 一般的な事務用 PC では遅すぎる可能性

### Option D: 業務用の有料手書き OCR (オンプレミス版)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low (導入は業者) |
| Cost | 高い (病院として契約する規模) |
| Scalability | 十分 |
| Team familiarity | — |

**Pros:** 手書きの精度が最も期待できる / サポートがある
**Cons:** 個人で入れる規模ではない / 病院の判断が要る

## Trade-off Analysis
この用途で一番重いのは**誤りの見えやすさ**。C は精度が高いが、誤りがもっともらしい文章として出てくるので、確認する人が気づけない。B は誤りの数が多く、結果の形も使いにくい。A は手書き認識の精度そのものは B と同じ部品に頼るが、
1. チェック欄を文字認識なしで確実に取れる
2. 欄ごとに答えの種類で誤りを弾ける (数字欄に漢字が出たら要確認)
3. 読めない欄は空欄＋画像として確認画面に残る

ので、**エンジンの精度が低くても安全側に倒れる**。登録の手間は、問診票が数種類なら最初の 1 回で済む。D は精度で勝るが費用と導入の判断が別の次元なので、A で足りなかった場合の次の手とする。

## Consequences
- **楽になる**: チェック欄の転記がなくなる / 複数枚の問診票を 1 つの CSV で一覧できる / 手書きエンジンを後から差し替えられる
- **難しくなる**: 問診票ごとのテンプレート作成と、書式改訂への追従 / 確認画面の分だけ画面が複雑になる / 配布サイズが増える (OpenCV、手書きモデル)
- **見直すこと**:
  - 評価で数字欄の自動確定率が 70% 未満 → 手書き欄は「画像＋人が入力」で固定
  - ~~PC にメモリ 16GB 以上や GPU/NPU がある → C を再検討~~ → 確認の結果メモリ 8GB・GPU なし (2026-10-23)。C は不採用で確定
  - 問診票が 4 種類以上 → テンプレートを画面で作る機能
  - A で足りない → D を病院に相談
