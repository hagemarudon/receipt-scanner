# 設計: 手書きの問診票への対応 (オフライン)

- 状態: 提案 (PC の仕様と問診票の実物を見てから確定)
- 対象: 現行版 (印刷物の文字起こし) に、手書きを含む問診票の読み取りを足す

## 1. 要件

### やること
| # | 内容 | 優先 |
| --- | --- | --- |
| F1 | 印刷物の文字起こし (現行どおり .txt / .csv / .pdf) | 済 |
| F2 | 問診票のチェック欄・「はい／いいえ」の○囲みを読み取る | 高 |
| F3 | 手書きの数字 (日付・年齢・身長・体重・体温) を読み取る | 中 |
| F4 | 手書きの自由記述 (症状・既往歴など) を読み取る | 低 (読めたら使う) |
| F5 | 自信のない欄は**画像と並べて表示し、人が確認・修正してから**保存する | 高 |
| F6 | 問診票 1 枚 = CSV の 1 行 (列 = 質問項目) で書き出せる | 中 |

### 守ること (非機能)
- **完全オフライン**: 通信なし。部品・モデルはすべてフォルダに同梱する
- **間違いを黙って出さない**: 機械が読めなかった欄を「それらしい文字」で埋めない。必ず「要確認」と分かるようにする
- **電子カルテ PC (Windows 10 IoT Enterprise LTSC、Core i7-10700、メモリ 8GB、GPU なし) の CPU だけで動く**: GPU は前提にしない。1 枚 30 秒以内が目安
- **フォルダごとコピーで導入できる**: インストーラ・管理者権限は使わない。サイズは USB で運べる範囲 (〜500MB)
- **実際の患者データを外に出さずに開発・評価する**: テストには家族が書いたダミーの問診票を使う

### 制約
- 開発者 1 人、利用者はパソコンに詳しくない
- PC は確認済み: Core i7-10700 (8 コア 16 スレッド)、メモリ 8GB。**電子カルテと同時に動くので、このアプリが使えるのは 1〜2GB 程度**と見る
- 日本語の手書き文字認識は、オフラインで使える無料の部品では精度が十分とは言えない (下の「4. 選択肢」)

## 2. 全体の流れ

```
 JPG / PDF
    │
    ▼
 [読み込み・向き補正]  ← 現行
    │
    ▼
 [書式の判定] ── 登録済みの問診票と一致? ──No──▶ [一般書類モード] 現行の Tesseract で全文 → 書き出し
    │Yes
    ▼
 [位置合わせ] 白紙の問診票の画像に、スキャンをぴったり重ねる (傾き・ずれを補正)
    │
    ▼
 [欄ごとに切り出し] テンプレートに書かれた枠の位置で切る
    │
    ├─ チェック欄・○囲み ──▶ 白紙との「インクの差」で判定           (確実)
    ├─ 印刷された欄       ──▶ Tesseract                              (確実)
    └─ 手書きの欄         ──▶ 手書き認識エンジン (差し替え可能) ＋ 信頼度
    │
    ▼
 [確認画面] 信頼度の低い欄を赤で表示。切り出し画像と認識結果を並べ、その場で修正
    │
    ▼
 [書き出し] CSV: 1 枚 1 行 / TXT: 「項目: 値」/ PDF: 元画像＋確認済みの文字
```

ポイントは**問診票を「テンプレート (どこに何が書かれるか)」として登録する**こと。書式が決まっているので、

- 欄の位置が分かる → 欄ごとに「数字だけ」「はい/いいえ」など答えの種類を絞れて精度が上がる
- 白紙と比べられる → チェックや○は「白紙より黒い部分が増えたか」で判定でき、文字認識が要らない
- 結果が「質問 → 答え」の形になる → CSV で 1 枚 1 行にできる

## 3. 詳細

### 3.1 テンプレート (問診票 1 種類につき 1 ファイル)

白紙の問診票のスキャン画像と、欄の定義 (JSON) の組。座標は白紙画像に対する割合 (0〜1) で持ち、解像度に依存させない。

```json
{
  "id": "monshin_v1",
  "name": "初診問診票",
  "reference_image": "monshin_v1.png",
  "fields": [
    {"id": "visit_date", "label": "記入日", "type": "date",   "box": [0.62, 0.08, 0.95, 0.12]},
    {"id": "age",        "label": "年齢",   "type": "number", "box": [0.70, 0.15, 0.85, 0.19]},
    {"id": "allergy",    "label": "アレルギー", "type": "choice",
     "options": [{"value": "あり", "box": [0.30, 0.40, 0.36, 0.43]},
                 {"value": "なし", "box": [0.40, 0.40, 0.46, 0.43]}]},
    {"id": "symptom",    "label": "症状",   "type": "text",   "box": [0.08, 0.50, 0.95, 0.65]}
  ]
}
```

- `type`: `checkbox` / `choice` (○囲み・チェック) / `number` / `date` / `text`
- 最初は問診票が数種類と想定し、**白紙のスキャンから開発側が手で作る**。種類が増えたら、枠をマウスで囲んで作る画面を足す (後回し)

### 3.2 書式の判定と位置合わせ
- 各テンプレートの白紙画像と、特徴点照合 (OpenCV の ORB → RANSAC で射影変換) を行う
- 対応点の一致数がしきい値を超えたテンプレートを採用し、その変換でスキャンを白紙の座標に重ねる
- どれとも一致しない・一致が弱いときは**一般書類モードに戻し**、画面に「問診票として読み取れませんでした」と出す
- 追加部品: `opencv-python-headless` (CPU のみ、数十 MB)

### 3.3 チェック欄・○囲み
- 位置合わせ後の欄を白黒にし、**白紙の同じ欄との差分**のインク量を測る
- `choice` は選択肢ごとの差分を比べ、1 つだけ明らかに多ければそれを答えにする。0 個・2 個以上なら「要確認」
- しきい値はダミーの問診票で決める

### 3.4 手書き認識 (差し替え可能にする)

```python
class HandwritingRecognizer(Protocol):
    def recognize(self, crop: Image.Image, kind: str) -> tuple[str, float]:
        """欄の画像 → (文字, 信頼度 0〜1)。kind は number / date / text"""
```

- 欄の種類で後処理をかける: `number` は数字以外を捨てる、`date` は「令和/西暦・年月日」の形に合わないものは信頼度を下げる、など
- 信頼度がしきい値未満なら値を空にして「要確認」。**読めない欄は空欄＋画像で残す**のが原則
- エンジンは 4 章の評価で選ぶ。評価前の初版は「手書き欄は画像の切り出しだけ出す (認識しない)」でも成り立つようにする

### 3.5 確認画面
- 左に問診票の画像 (欄を枠で表示)、右に「項目・値・信頼度」の一覧
- 要確認の欄を上にまとめ、赤で表示。欄を選ぶと切り出し画像を大きく表示し、値をその場で修正
- 「確定して保存」で書き出し。修正した欄は記録 (自動 / 手入力) を残す

### 3.6 書き出し
| 形式 | 問診票モードの中身 |
| --- | --- |
| CSV | 1 枚 1 行。列 = ファイル名・各質問。複数枚を 1 つの CSV にまとめられる |
| TXT | 「年齢: 72」のように 1 行 1 項目。要確認の欄は「(要確認)」 |
| PDF | 元の画像＋確認済みの値を透明テキストで重ねたもの |

### 3.7 データの持ち方
```
FormResult
  template_id, source_file, page
  fields: [ {id, label, value, confidence, status: auto | needs_review | edited, crop: 画像} ]
```

## 4. 選択肢とトレードオフ

### 4.1 問診票をどう読むか

| 方式 | 手間 | 精度 | 結果の形 | 判断 |
| --- | --- | --- | --- | --- |
| **A. テンプレート方式** (上の設計) | 問診票ごとに登録が要る | チェック欄はほぼ確実、手書きも欄ごとに答えの種類を絞れる | 質問 → 答え | **採用** |
| B. テンプレートなし (全文を手書き対応エンジンに通す) | 登録不要 | チェック・○は読めない。手書きと印刷が混ざり順番も崩れやすい | ただの文章 | 不採用 (一般書類モードとしては残る) |

問診票は書式が数種類で固定されているはずなので、登録の手間は最初の 1 回だけ。チェック欄を確実に取れる利点が大きい。

### 4.2 手書き認識のエンジン

| 候補 | オフライン | CPU だけで | 日本語の手書き | 同梱サイズ | 懸念 |
| --- | --- | --- | --- | --- | --- |
| Tesseract (現行) | ○ | ○ | × ほぼ読めない | 済 | 比較の基準としてだけ使う |
| PaddleOCR PP-OCRv5 | ○ | ○ (軽量版あり) | △ 日本語・手書き対応をうたうが、日本語手書きの精度は未確認 | 中 (100MB 前後の見込み) | 実物で評価が必要 |
| NDLOCR-Lite (国立国会図書館) | ○ | ○ | △ 手書きは「実験的」扱い (紹介記事による。要確認) | 中 | 主目的は活字 |
| PC 内で動かす大きな画像言語 AI | ○ | △ 1 枚数分かかりうる | ○ 一番強い | 大 (数 GB) | **読めない字をそれらしく補う**。医療では危険。メモリ 16GB 以上が要る |
| 業務用の有料手書き OCR (オンプレミス版、例: リコーの AI 日本語手書き OCR) | ○ | ○ | ○ | — | 費用。個人で入れるのは難しい |

**決め方**: 家族がダミーで書いた問診票 (きれいな字・くずした字・高齢者風) 10 枚程度で、PaddleOCR と NDLOCR-Lite を欄の種類ごとに比べる。見る数字は

- **自動確定率**: 信頼度がしきい値以上で、人の確認なしに確定できた欄の割合
- **自動確定した欄の誤り率**: これが 1% を超えるなら、しきい値を上げる (確認の手間が増えても誤りを減らす方を優先)

どちらも数字欄で自動確定率 70% に届かなければ、手書き欄は「画像の切り出し＋人が入力」で運用し、エンジンは入れない。

## 5. 性能の見積もり (Core i7-10700・メモリ 8GB・GPU なし)

| 処理 | 1 枚 (A4・300dpi) あたり |
| --- | --- |
| 読み込み・向き補正 | 1〜2 秒 |
| 書式判定・位置合わせ (テンプレート数枚) | 1〜2 秒 |
| チェック欄 (差分) | 0.1 秒未満 |
| 手書き欄 30 個の認識 (軽量モデル) | 数秒 |
| 印刷欄 (Tesseract) | 数秒 |
| **合計** | **10〜20 秒程度** (目標 30 秒以内) |

メモリは手書きモデルを含めて 1GB 未満の見込み。1 日数十枚なら速さは問題にならない。数字は評価のときに実機で測り直す。

## 6. 失敗したときの扱い
| 状況 | 動き |
| --- | --- |
| どのテンプレートとも合わない | 一般書類モードで全文を出し、「問診票として読み取れませんでした」と表示 |
| 位置合わせが不安定 (一致点が少ない) | 同上。無理に欄を切らない |
| チェックが 0 個・2 個以上 | その欄を要確認に |
| 手書きの信頼度が低い | 値を空にして要確認。画像は必ず残す |
| 手書きエンジンが入っていない・壊れている | 手書き欄は画像だけ出し、チェック欄と印刷欄は通常どおり |

## 7. 段階
1. **今**: 印刷物版を実機 (Windows 10 IoT Enterprise LTSC) で動かし、起動・速度・見た目を確認
2. **第 1 段階**: テンプレート・位置合わせ・チェック欄・確認画面・CSV 1 枚 1 行。手書き欄は**画像の切り出しのみ**
3. **第 2 段階**: 4.2 の評価をして、基準を満たしたエンジンを手書き欄に組み込む
4. **必要なら**: テンプレートを画面で作る機能 (問診票が 4 種類以上になったら)

第 1 段階だけでも「チェック欄の転記がなくなる」「手書き欄が一覧で見られる」効果がある。手書き認識の精度に左右されない部分を先に作る。

## 8. 今後見直すこと
- **確認済み: メモリ 8GB・GPU なしなので、PC 内の画像言語 AI は使わない** (将来メモリ 16GB 以上や GPU のある PC に替わったら、「確認画面での候補表示」に限って再検討)
